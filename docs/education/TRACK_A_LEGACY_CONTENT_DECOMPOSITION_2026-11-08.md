## 1. Решение и область применения

Этот документ завершает содержательную декомпозицию трёх legacy-уроков на уровне разделов, learning outcomes, лабораторных работ и проверочных заданий. Он определяет целевые display codes в утверждённой программе и правила переноса материалов.

**Это карта миграции контента, не production-миграция.** Текущие legacy IDs, URL, RU/EN/中文 страницы, записи catalog v1/v2, prerequisites, planet IDs, bookmarks, progress и статусы не меняются. Новые технические UID будут созданы отдельно в schema/catalog v3 после фиксации mapping и compatibility contract.

Термины в таблицах:
- **Перенести** — содержательный фрагмент подходит целевому уроку после языковой и педагогической редакции.
- **Разделить** — материал содержит несколько независимых учебных задач.
- **Сохранить как lab** — практическая часть остаётся сопровождающим ресурсом, а не отдельным уроком.
- **Не покрывает** — legacy материал не содержит достаточного объяснения; соответствующий новый урок нужно разработать.
- **Справочный блок** — материал не должен занимать основное время урока и не образует новый модуль.

### 3.2. Целевое распределение содержания A.6

**1.4.3 — Переобучение и недообучение**
- определения underfitting / overfitting;
- сравнение train и validation error;
- bias–variance как концептуальная рамка;
- learning curves и диагностические паттерны;
- методы уменьшения overfitting и исправления underfitting;
- разбор моделей A/B/C и практические диагностические упражнения.

**1.4.4 — Обобщающая способность модели**
- что именно означает generalization;
- отличие качества на обучающей выборке от качества на новых объектах;
- зависимость вывода от репрезентативности данных и целевого сценария применения;
- ограничения эмпирической оценки будущего качества;
- связь объёма/разнообразия данных, устойчивых закономерностей и переноса.

**1.5.6 — Кросс-валидация и устойчивость результатов**
- K-fold и повторная оценка;
- temporal split для временных прогнозов;
- group split для повторяющихся объектов;
- риск утечки между train/validation/test;
- выбор протокола в соответствии с реальным сценарием;
- независимый test set и запрет подгонки решения под test после просмотра результата.

**1.2.6 — Корреляция, зависимости и утечка данных**
- природа target leakage;
- дубликаты и связанные наблюдения как источники утечки;
- пример соседних часов одного здания и разделения по объекту/времени;
- различие между корреляцией и причинностью.

### 3.3. Важные педагогические исправления

1. Не говорить, что validation error является прямым измерением истинной будущей ошибки. Это оценка, зависящая от протокола и выборки.
2. Не трактовать train–validation gap как достаточное доказательство overfitting.
3. Не переносить dropout и DL-specific регуляризацию в базовый урок без контекста; дать короткий пример и ссылку на Theme 3.
4. Не смешивать regularization, early stopping, cross-validation и data splitting: это разные механизмы и этапы экспериментального процесса.
5. Не использовать test set для итеративного выбора модели. Если решение меняется после просмотра test, этот набор больше не является независимой финальной оценкой.
6. Указать, что random split может быть некорректен для временных и групповых данных.

### 4.3. Решение по Python mini-lab

Текущий скрипт `xai-a1-2-1-passport.py` использует фиксированную синтетическую линейную score-модель:
- score не является вероятностью;
- модель не обучается;
- алгебраические вклады относительно baseline не являются полноценным SHAP;
- изменение одного признака показывает чувствительность заданной формулы, а не причинный эффект реального мира.

**Решение:** сохранить как короткую вводную демонстрацию атрибуции в 4.2.4 (с обязательным предупреждением о статусе игрушечной модели) либо как необязательный ресурс к 4.2.1. Не переносить этот lab в 4.6 и не переименовывать его в SHAP lab. Для 4.6 нужен отдельный корректный эксперимент с SHAP explainer, background dataset и проверкой суммы вкладов.

Файл-инструкция `A1_2_1_XAI_LAB.md` следует обновить после утверждения нового UID: в ней нужно объяснить назначение score, baseline, локальных вкладов, ограничения и воспроизводимый результат. До этого сохранить legacy filename.

### 4.4. Что делать с регулированием

Раздел регулирования содержит полезные оговорки, но он не является центральным учебным результатом модуля «Таксономия XAI и важность признаков». Рекомендуется:
- оставить 1–2 абзаца контекста в 4.2.1 или вынести в optional reading;
- сохранить отдельные первичные ссылки EU AI Act, GDPR и ГОСТ Р 59276-2020;
- фиксировать дату последней проверки и область применения каждого утверждения;
- перед публикацией перепроверить актуальные редакции и даты применения;
- не представлять объяснение модели как автоматическое доказательство compliance, fairness, safety или causal validity.

### 4.5. Prerequisites для нового вводного XAI-блока

Текущая ссылка на старые IDs A.1.1.1–A.1.1.6 не должна переходить в новую модель как постоянная зависимость. В целевом каталоге prerequisites задаются UID уроков/модулей, а содержательно должны включать:
- данные, признаки и целевую переменную (Theme 1 / Module 2);
- типы ML и постановки задач на базовом уровне (Module 3);
- модель, параметры и прогноз (Module 4);
- обобщение, переобучение и недообучение (Module 4);
- базовую оценку качества модели (Module 5).

Не требовать прохождения всей Theme 2 и Theme 3 для понимания вводного XAI, если конкретный урок не использует Python или внутреннее устройство нейросети. Для отдельных labs prerequisites уточняются отдельно.

## 6. Требования к модели каталога v3, вытекающие из декомпозиции

1. Разделить сущности `Track`, `Theme`, `Module`, `Lesson`, `Resource` и `LegacyAlias`.
2. Каждая сущность получает неизменяемый технический UID. Display code хранится отдельно и может изменяться без смены UID.
3. Lesson должен иметь один текущий parent Module UID. Один legacy lesson может отображаться как archive/landing и ссылаться на несколько target Lesson UIDs.
4. Для переноса отдельных частей legacy lesson нужна сущность/таблица content mapping: `legacy_lesson_uid`, `legacy_section_key`, `target_lesson_uid`, `mapping_type`, `editorial_status`, `notes`.
5. `LegacyAlias` должен поддерживать старые IDs и URL, включая языковые URL, и вести на target lesson, archive page или landing page.
6. Prerequisites связываются по UID, не по display code и не по порядку строк в JSON.
7. Progress, bookmarks и quiz attempts сохраняют ссылку на исходный legacy UID/alias и имеют явное правило переноса на один или несколько новых уроков. Не копировать завершённый прогресс на все фрагменты composite lesson автоматически.
8. Planet map должна ссылаться на UID опубликованных target lessons; legacy composite page не становится автоматически отдельной planet card.
9. Статусы `published`, `review`, `draft`, `archived` должны быть явными. Смена статуса не должна происходить как побочный эффект миграции.
10. Для каждой языковой версии нужен единый lesson UID и отдельные locale resources с проверкой полноты перевода.
11. Поддержать dual-read/compatibility adapter на период миграции v1/v2 → v3.
12. Перед production switch выполнить round-trip и consumer tests для URL, aliases, locales, prerequisites, progress, bookmarks, quizzes, planets, breadcrumbs, admin UI и API.
