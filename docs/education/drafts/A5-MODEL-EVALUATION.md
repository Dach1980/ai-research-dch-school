# A.5 — Как проверяют качество модели

**Планируемая длительность:** 60–70 минут  
**Prerequisites:** A.1–A.4

## 1. Зачем проверять модель

Модель может показывать почти идеальный результат на примерах, на которых обучалась, и при этом плохо работать в реальной эксплуатации. Более того, неверно выбранная метрика способна создать иллюзию качества: система может почти всегда выдавать один и тот же ответ и получать высокий процент правильных ответов, хотя пропускает все редкие аварийные события.

Главный вопрос урока: **какие эксперименты позволяют оценить качество модели честно и понять, подходит ли она для поставленной задачи?**

## 2. Результаты обучения

После урока учащийся сможет:
1. объяснить назначение обучающей, валидационной и тестовой выборок;
2. выбирать базовые метрики регрессии и классификации;
3. интерпретировать confusion matrix, precision, recall и F1;
4. объяснить, почему accuracy бывает бесполезна при дисбалансе классов;
5. распознавать переобучение, недообучение и утечку данных;
6. описать ограничения оценки и обосновать, какие выводы она позволяет сделать.

## 3. Интуиция: экзамен, ответы и независимая проверка

Представим, что ученик много раз решает один и тот же набор задач и запоминает ответы. На знакомых задачах результат будет отличным. Но это ещё не показывает, сможет ли он решить новые задачи того же типа.

С моделью аналогично. Если мы используем тестовые ответы для подбора модели, тест перестаёт быть независимой проверкой. Поэтому данные нужно разделять по назначению, а правила эксперимента фиксировать до просмотра итогового результата.

## 4. Разделение данных: train, validation и test

- **Training set (обучающая выборка)** — используется для настройки параметров модели.
- **Validation set (валидационная выборка)** — используется для сравнения конфигураций, выбора гиперпараметров и принятия решений о модели.
- **Test set (тестовая выборка)** — используется для итоговой оценки выбранного решения на данных, не участвовавших в его подборе.

Типовая схема — 70/15/15 или 80/10/10, но универсального соотношения нет. Оно зависит от размера набора, редкости событий, структуры данных и задачи. При небольших выборках может быть полезна кросс-валидация.

**Критическое правило:** если мы многократно меняем модель, ориентируясь на test score, мы фактически начинаем подгонять решение под тест. Итоговая оценка становится оптимистичной.

## 5. Базовая линия (Baseline)

**Baseline (базовая линия)** — простое решение, с которым сравнивают более сложную модель. Для регрессии это может быть прогноз средним или медианой обучающей выборки. Для классификации — наиболее частый класс или заранее заданное простое правило.

Если сложная модель не превосходит разумную базовую линию, необходимо выяснить почему. Сложность и вычислительная стоимость сами по себе не являются преимуществом.

## 6. Метрики регрессии

Пусть yᵢ — правильное значение, ŷᵢ — прогноз, n — число примеров.

### 6.1 MAE — средняя абсолютная ошибка

`MAE = (1/n) · Σ |ŷᵢ − yᵢ|`

Показывает среднюю величину абсолютного отклонения. Измеряется в тех же единицах, что и целевая переменная. Например, MAE = 120 кВт·ч означает, что среднее абсолютное отклонение составляет 120 кВт·ч.

### 6.2 MSE — средняя квадратичная ошибка

`MSE = (1/n) · Σ (ŷᵢ − yᵢ)²`

Квадрат ошибки сильнее штрафует большие отклонения. Единицы измерения также возводятся в квадрат, поэтому интерпретировать MSE в прикладном смысле бывает менее удобно.

### 6.3 RMSE — корень из средней квадратичной ошибки

`RMSE = √MSE`

Возвращает метрику в исходные единицы целевой переменной, но сохраняет повышенную чувствительность к большим ошибкам.

### 6.4 R² — коэффициент детерминации

`R² = 1 − SS_res / SS_tot`

Сравнивает ошибку модели с вариантом прогнозирования средним значением целевой переменной. R² = 1 соответствует идеальному совпадению на оцениваемых данных; R² = 0 — результату на уровне такого базового прогноза; значение может быть отрицательным, если модель хуже базовой линии. R² не означает «процент правильных прогнозов» и не доказывает причинность.

## 7. Метрики классификации

Для бинарной классификации модель относит объект к положительному или отрицательному классу. Результаты удобно свести в матрицу ошибок.

| Фактический класс / прогноз | Положительный прогноз | Отрицательный прогноз |
|---|---|---|
| Положительный класс | TP — верно найденный положительный | FN — пропущенный положительный |
| Отрицательный класс | FP — ложная тревога | TN — верно найденный отрицательный |

- **TP (True Positive):** событие есть, модель его обнаружила.
- **TN (True Negative):** события нет, модель правильно сказала «нет».
- **FP (False Positive):** ложная тревога.
- **FN (False Negative):** пропуск события.

### 7.1 Accuracy — доля правильных ответов

`Accuracy = (TP + TN) / (TP + TN + FP + FN)`

Полезна, когда классы сопоставимы по частоте и стоимость ошибок не слишком различается. При редких событиях может вводить в заблуждение.

### 7.2 Precision — точность положительных прогнозов

`Precision = TP / (TP + FP)`

Отвечает на вопрос: какая доля положительных сигналов модели действительно оказалась положительной? Высокая precision означает меньше ложных тревог.

### 7.3 Recall — полнота обнаружения

`Recall = TP / (TP + FN)`

Отвечает на вопрос: какую долю всех реальных положительных случаев удалось обнаружить? Высокий recall означает меньше пропусков.

### 7.4 F1-score

`F1 = 2 · Precision · Recall / (Precision + Recall)`

Гармоническое среднее precision и recall. Удобно для компактного сравнения, но не отражает все последствия ошибок и не заменяет анализ матрицы ошибок.

## 8. Почему accuracy может обмануть

Предположим, в архиве 1000 проверок оборудования, и только 10 случаев действительно аварийные. Модель всегда говорит «аварии нет».

Она правильно классифицирует 990 случаев из 1000:

`Accuracy = 990 / 1000 = 99%`

Но при этом:
- TP = 0;
- FN = 10;
- recall = 0%;
- все аварии пропущены.

Формально accuracy высока, но для задачи обнаружения аварий модель бесполезна. Это пример **Class Imbalance (дисбаланса классов)** — сильного различия в частоте классов.

## 9. Порог решения и компромисс precision–recall

Многие классификаторы выдают оценку или вероятность принадлежности к классу. Чтобы превратить её в категорию, выбирают **Threshold (порог)**. Например, если оценка выше 0.5, система выдаёт положительный класс.

При снижении порога модель чаще отмечает положительный класс: recall обычно растёт, но могут увеличиться ложные тревоги и снизиться precision. При повышении порога сигналов меньше, precision может вырасти, но часть реальных событий будет пропущена.

Порог следует выбирать с учётом последствий:
- если пропуск опасного события крайне дорог, приоритет может быть у recall;
- если ложная тревога запускает дорогостоящую остановку, важнее контролировать precision;
- в критичных сценариях рассматривают стоимость каждого типа ошибки, а не только одну метрику.

## 10. Переобучение и недообучение

- **Underfitting (недообучение):** модель не улавливает даже устойчивые закономерности обучающих данных.
- **Overfitting (переобучение):** модель чрезмерно подстраивается под обучающие примеры и шум.
- **Generalization (обобщение):** способность сохранять приемлемое качество на новых данных.

Типичный сигнал переобучения — низкая ошибка на train и заметно более высокая на validation. Но сам по себе разрыв не объясняет причину: нужно проверить данные, разделение, сложность модели и процедуру обучения.

## 11. Data Leakage — утечка данных

Утечка возникает, когда в обучение или оценку попадает информация, которая недоступна в момент реального прогноза или раскрывает целевой ответ.

Примеры:
1. Прогнозируем завтрашний расход, но используем итоговый счётчик за завтра.
2. Нормализуем всю таблицу до разделения на train и test, используя статистики тестовых данных.
3. Случайно распределяем почти одинаковые дубликаты между train и test.
4. Для временного прогноза случайно перемешиваем даты и обучаемся на будущем относительно тестового периода.
5. В признаках есть поле, которое формируется только после наступления целевого события.

Правильный принцип: все преобразования, параметры которых оцениваются по данным (например, среднее для стандартизации), обучаются только на training set, а затем применяются к validation/test без повторной подгонки.

## 12. Как правильно разделять данные

- **Random split:** случайное разделение может подойти для независимых однотипных наблюдений.
- **Time-based split:** для прогноза будущего обучаемся на прошлом, проверяемся на более позднем периоде.
- **Group split:** связанные наблюдения одного здания, пациента, пользователя или устройства должны оставаться в одной части, если в реальности мы хотим обобщать на новые группы.
- **Cross-validation (кросс-валидация):** несколько повторных разбиений, позволяющих оценить вариативность результата. Тестовая выборка при этом остаётся отдельной финальной проверкой.

## 13. Практический эксперимент

**Задача:** обнаружение редких аварийных событий.

1. Создать или взять размеченный набор, где положительный класс встречается редко.
2. Обучить простую модель классификации.
3. Сравнить её с baseline «всегда нормальное состояние».
4. Рассчитать accuracy, precision, recall и F1.
5. Посмотреть confusion matrix.
6. Изменить порог классификации.
7. Объяснить, как изменились ложные тревоги и пропуски.
8. Сформулировать, какой компромисс подходит конкретному сценарию и почему.

**Критерий успешного эксперимента:** учащийся не просто называет лучшую метрику, а связывает выбор с последствиями FP и FN и ограничениями данных.

## 14. Ограничения оценки

- Оценка на тестовой выборке не гарантирует качество при изменении среды.
- Ошибки разметки ограничивают достижимое качество и достоверность метрик.
- Маленькая выборка даёт нестабильную оценку; полезно показывать диапазон или разброс.
- Средняя метрика может скрывать плохое качество на отдельных группах.
- Условия эксплуатации могут отличаться от условий теста.
- После запуска нужны мониторинг, контроль сдвига данных и повторная оценка.

## 15. Словарь

- **Training set:** данные для настройки параметров.
- **Validation set:** данные для выбора конфигурации.
- **Test set:** независимые данные для итоговой оценки.
- **Metric:** числовой критерий качества.
- **Baseline:** простое решение для сравнения.
- **MAE / MSE / RMSE:** метрики ошибки регрессии.
- **R²:** сравнение объяснённой вариации с базовым прогнозом средним.
- **Confusion matrix:** матрица TP, TN, FP, FN.
- **Precision:** доля верных положительных прогнозов среди всех положительных прогнозов.
- **Recall:** доля найденных положительных случаев среди всех реальных положительных.
- **F1-score:** гармоническое среднее precision и recall.
- **Threshold:** порог преобразования оценки модели в класс.
- **Class imbalance:** дисбаланс частот классов.
- **Cross-validation:** повторная оценка на нескольких разбиениях.
- **Data leakage:** попадание недопустимой информации в обучение или оценку.
- **Distribution shift:** изменение распределения данных при применении.

## 16. Проверка понимания

1. Для чего нужна test set?  
   **Ответ:** для итоговой независимой оценки уже выбранной модели.
2. Почему нельзя подбирать гиперпараметры по test set?  
   **Ответ:** тест перестаёт быть независимым и оценка становится оптимистичной.
3. Что важнее при обнаружении редких опасных событий — accuracy или recall?  
   **Ответ:** часто recall важнее, но окончательный выбор зависит от цены пропуска и ложной тревоги.
4. Что означает FN?  
   **Ответ:** реальное положительное событие, которое модель не обнаружила.
5. Почему нельзя использовать будущие измерения для прогноза прошлого или будущего?  
   **Ответ:** это утечка информации и нарушение реального сценария применения.

## 17. Обязательные иллюстрации к финальной версии

1. Разделение train / validation / test с указанием, какие решения принимаются на каждой части.
2. Матрица ошибок 2×2 с TP, TN, FP, FN.
3. Три кривые train/validation loss для underfitting, разумного обучения и overfitting.
4. График компромисса precision–recall при изменении threshold.
5. Временная шкала: корректное хронологическое разделение против случайного перемешивания с утечкой будущего.
