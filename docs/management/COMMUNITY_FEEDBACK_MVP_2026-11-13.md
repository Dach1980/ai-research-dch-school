# DCH School — регистрация и обратная связь сообщества

**Дата:** 2026-11-13  
**Статус:** регистрация заблокирована; базовый почтовый канал вопросов и пожеланий реализован без регистрации  
**Принцип:** сайт и обучение остаются бесплатными; в MVP нет платежей, подписок, платных уровней или сбора платёжных реквизитов.

## 1. Цель

Открыть сайт для ранних пользователей и получать от них структурированные замечания, вопросы и предложения, не превращая публичный сайт в неуправляемый форум.

Пользователь после регистрации сможет:
- задать вопрос по уроку или учебной программе;
- сообщить об ошибке, неточности, неработающей ссылке или проблеме отображения;
- предложить улучшение урока, перевода, иллюстрации, навигации или сайта;
- видеть статус собственных обращений и ответ школы.

На первом этапе обращения видны только автору и уполномоченным администраторам. Публикация вопросов и ответов для всех пользователей — отдельное последующее решение после появления модерации.

## 2. Что уже существует

- Supabase project `dch-school`, регион `eu-central-1`.
- Supabase Auth уже подключён в `scripts/auth.js`: email/password, подтверждение email, вход, повторная отправка письма и восстановление пароля.
- Есть таблица `public.profiles` с именем и языком интерфейса.
- Есть `public.school_admins` для ролей owner/editor.
- `scripts/supabase-config.js` содержит `registrationEnabled: false`.
- Страница `auth/index.html` уже содержит переключение входа/регистрации, но регистрация намеренно закрыта.
- `docs/legal/TERMS_DRAFT.md` и `docs/legal/PRIVACY_POLICY_DRAFT.md` явно помечены как неутверждённые черновики. Политика конфиденциальности требует определить оператора, цели, основания, сроки хранения, получателей и права пользователей. Владелец предоставил публичный контактный email itprof80@gmail.com; его работоспособность ещё не проверена.
- История миграций в подключённом Supabase API на момент аудита возвращает пустой список, хотя таблицы уже существуют. До новых DDL-изменений нужно сверить фактическую схему с историей и репозиторием, чтобы не создавать конфликтующую миграцию.

## 3. Архитектурное решение

**Не создавать вторую систему авторизации.** Использовать текущий Supabase Auth и профиль пользователя. Публичный браузер получает только publishable/anon key; service-role/secret key никогда не попадает в HTML или JS.

Предлагаемый поток:
1. Посетитель открывает страницу аккаунта и регистрируется по email.
2. Supabase отправляет подтверждение email на разрешённый redirect URL.
3. Только подтверждённый пользователь может отправить обращение.
4. Браузер сохраняет обращение через Supabase Data API с действующей пользовательской JWT-сессией.
5. RLS проверяет владельца записи; пользователь видит только свои обращения.
6. Администратор с активной записью в `school_admins` просматривает и меняет статус обращения.
7. Публичная часть сайта показывает только опубликованные школой ответы/FAQ, без email, имени или иных личных данных автора.

## 4. Модель данных MVP

Предлагаемая таблица `public.community_feedback`:

| Поле | Тип / смысл |
|---|---|
| `id` | UUID, primary key |
| `user_id` | UUID, FK → `auth.users.id`, not null |
| `kind` | `question`, `bug`, `content_issue`, `idea` |
| `title` | Краткий заголовок, ограничение длины |
| `body` | Подробное описание, ограничение длины |
| `page_url` | URL страницы, где возник вопрос/ошибка |
| `lesson_uid` | Необязательный стабильный UID урока |
| `locale` | `ru`, `en`, `zh` |
| `status` | `new`, `triaged`, `in_progress`, `answered`, `resolved`, `declined` |
| `admin_reply` | Ответ школы, видимый автору после сохранения |
| `created_at`, `updated_at` | Временные метки |

В первой версии не принимать вложения и не давать пользователям редактировать статус или ответ администратора. Публичный флаг не добавлять до готовности правил публикации и согласия автора.

## 5. Безопасность и RLS

- RLS включён обязательно.
- `INSERT`: только роль `authenticated`, и только если `user_id = auth.uid()`.
- `SELECT`: пользователь читает только собственные записи; администратор — все записи при активной роли `school_admins`.
- Пользователь не может менять `user_id`, `status` или `admin_reply`.
- Администраторские изменения выполняются только через защищённую административную поверхность с проверкой роли на серверной стороне или отдельной ограниченной политикой.
- Не использовать `user_metadata` для авторизации.
- Проверить grants Data API отдельно от RLS.
- Ограничить размер заголовка/текста и частоту отправки; экранировать пользовательский текст при отображении.
- Перед публичной регистрацией включить CAPTCHA (Turnstile или hCaptcha) и проверить ограничения Auth.
- Не публиковать адреса электронной почты, профили и необработанные обращения.

## 6. Интерфейс MVP

### В аккаунте
- Состояния «Войти», «Создать аккаунт», «Подтвердить email», «Восстановить пароль».
- После входа — раздел «Мои обращения».
- Форма с типом обращения, заголовком, описанием, текущим URL, необязательным UID урока и языком.
- История статусов и ответ администратора.

### На страницах уроков
- Ненавязчивая ссылка «Задать вопрос / Сообщить об ошибке».
- При переходе форма автоматически получает URL страницы, код урока и язык.
- В RU / EN / 中文 локализованы форма, статусы, подтверждения и ошибки.

### Для администратора
- Очередь новых обращений.
- Фильтры по типу, статусу, уроку и локали.
- Ответ автору, изменение статуса, внутренние заметки (не видны автору).
- Сводные числа для Audit & Roadmap без персональных данных.

## 7. Бесплатный режим

- Все опубликованные уроки остаются открытыми без оплаты.
- Регистрация бесплатная и нужна только для отправки/отслеживания обращений и будущих учебных функций.
- Не подключать Stripe, платежи, тарифы, paywall или платные роли.
- Существующие технические поля платного доступа не использовать для ограничения новых уроков.

## 8. Блокирующие условия запуска регистрации

Регистрация остаётся выключенной до выполнения всех пунктов:
- [ ] Утверждены юридические документы: оператор/контакты, юрисдикция, цели и основания обработки, сроки хранения, права пользователя, удаление аккаунта и данных.
- [ ] Подготовлены публичные локализованные страницы Terms и Privacy; текущие Markdown-файлы остаются черновиками.
- [ ] Настроен и проверен SMTP отправитель: подтверждение email, повторная отправка и сброс пароля.
- [ ] Настроены Supabase Site URL и точные Redirect URLs для `https://dchai.ru` и локальной разработки.
- [ ] Проверена CAPTCHA и Auth rate limits.
- [ ] Проверены RLS, grants и Supabase Security Advisors; отдельно устранены или обоснованы существующие предупреждения по публично исполняемым SECURITY DEFINER-функциям и leaked-password protection.
- [ ] Проверены удаление аккаунта, запрос на удаление данных и контакт для обращений по приватности.
- [ ] Проведён тест регистрации, подтверждения email, входа, восстановления пароля и выхода на RU / EN / 中文.

## 9. Этапы реализации

**Этап 0 — аудит и проектирование (текущий):** проверить Auth, юридические ограничения, таблицы, политики и фактическую конфигурацию Supabase; утвердить схему обращений.

**Этап 1 — база и безопасность:** согласовать migration plan, создать community_feedback, индексы, ограничения, RLS и тесты; проверить Security Advisors. Не выполнять DDL в production до подтверждения соответствия миграции фактической схеме.

**Этап 2 — пользовательский MVP:** включить регистрацию после закрытия legal/email gates; реализовать форму и «Мои обращения» на трёх языках.

**Этап 3 — модерация:** добавить защищённую административную очередь, ответы и статусы; журналировать административные действия.

**Этап 4 — публичные ответы:** только после появления правил публикации и отдельного согласия автора публиковать обезличенные FAQ/ответы.

## 10. Критерии готовности

- Пользователь может зарегистрироваться, подтвердить email, войти и восстановить пароль.
- Неподтверждённый и анонимный посетитель не может создавать обращения.
- Пользователь A не может читать обращения пользователя B или менять чужие данные.
- Администратор может отвечать и менять статус; пользователь видит ответ в своём аккаунте.
- Пользовательский текст безопасно экранируется; есть ограничения длины и частоты.
- Форма и статусы работают на трёх языках и мобильных экранах.
- Никакая личная информация не появляется в публичном каталоге, карте знаний или Audit.
- Все функции бесплатны; платёжные провайдеры отсутствуют.
- Ручные проверки email, CAPTCHA, RLS и UI отражены отдельно от автоматических тестов.


## 11. Дополнение после определения юрисдикции (2026-11-13)

Владелец определил Российскую Федерацию как юрисдикцию проекта. При этом техническая проверка показала, что действующий Supabase project `dch-school` размещён в `eu-central-1` (Frankfurt, Germany), а в нём уже есть Auth users и `public.profiles`. Это блокирует открытие регистрации граждан РФ в текущей архитектуре до отдельного юридического заключения и выбора соответствующей требованиям первичной базы в РФ.

Не создавать `community_feedback` в текущей немецкой базе как хранилище персональных обращений российских пользователей. Сначала выбрать российскую инфраструктуру для первичного хранения, спроектировать перенос Auth/profile и только затем выполнять миграцию таблицы обращений. Не переносить новые пользовательские данные до утверждения архитектуры.

Security Advisor дополнительно подтверждает предупреждения по исполняемым SECURITY DEFINER-функциям и отключённой leaked-password protection. CAPTCHA в текущем клиентском auth-коде не обнаружена. Настройки SMTP и Auth redirect URLs не подтверждены; это требует отдельной проверки Dashboard/провайдера.

Подробности и источники: `docs/legal/RUSSIA_DATA_LOCALIZATION_REVIEW_2026-11-13.md`.


## 12. Отдельный публичный канал обратной связи без регистрации (2026-11-13)

По решению владельца регистрация остаётся выключенной до выбора российской первичной инфраструктуры и завершения юридической проверки. Чтобы не останавливать сбор пожеланий по открытому сайту, реализована отдельная статическая форма, которая только формирует письмо через почтовое приложение посетителя.

- Страницы: `feedback/index.html`, `feedback/index-en.html`, `feedback/index-zh.html`.
- Адрес получателя: `itprof80@gmail.com`.
- Общая навигация добавляет ссылку на форму для RU / EN / 中文.
- Поля: тип сообщения, имя (необязательно), email для ответа (необязательно), URL страницы (необязательно), текст сообщения.
- Отправка выполняется только после подтверждения пользователем в его почтовом приложении.
- Форма не отправляет данные в Supabase, не создаёт записи в базе, не использует сторонний сервис обработки форм и не обещает серверного подтверждения доставки.
- Если у посетителя не настроено почтовое приложение, он может вручную написать на указанный адрес.
- Это временный низкорисковый канал обратной связи, а не замена полноценной системе обращений с историей, статусами и модерацией.

Проверить в браузере: открытие формы из RU / EN / 中文 страниц, автозаполнение URL исходной страницы, работу mailto на desktop/mobile и доступность резервной ссылки на email. Регистрация остаётся закрытой; RM-28 не разблокируется этим изменением.
