# Решение о канонической архитектуре учебных программ DCH

**Дата фиксации:** 2026-11-11  
**Статус:** принятое ранее решение Track A подтверждено; Track B и общая база сохраняют статус рабочей архитектуры до поурочной спецификации.

## 1. Иерархия

Единая иерархия школы: **Track → Theme → Module → Lesson**. Track A/B/C сохраняются. UID каталога является техническим стабильным идентификатором; человекочитаемый код и URL — отдельные поля. При миграции старые ID и URL сохраняются через alias registry.

## 3. Каноническая модель 40-модульной программы

Счётчик 0–39 — сквозная исследовательская программа Track A/B, но не 40 одинаково утверждённых модулей.

- **0–10 — общая фундаментальная база.** Рабочая реконструкция. Состав, outcomes и assessment требуют полной спецификации.
- **11–26 — Track A / Understanding AI.** 16 модулей, утверждённая архитектура 2026-11-05. Содержание и границы модулей нельзя менять без решения и записи в audit log.
- **19–25 — переходная область A → B.** CNN, gradients, CAM, concepts, attention, applied LLM и agent behaviour. Это не дублирование и не обязательное повторное прохождение для тех, кто подтвердил компетенции.
- **27–39 — Track B / Inside AI.** Рабочее ядро Mechanistic Interpretability, Safety и исследовательских методов. Структура направлений принята как целевая, но отдельные модули и практики требуют детализации и утверждения.
- **Track C / Building with AI — отдельная программа C0–C12**, не входит в счётчик 40.

Неизменяемые решения:
- 14 и 15 — самостоятельные модули; causal identification предшествует heterogeneous effects.
- 26 — самостоятельный модуль оценки качества; attacks — отдельный advanced block.
- SHAP axioms остаются в модуле 17; deep dives — лаборатории, не дублирующие модули.
- 24 и 25 разделяют анализ LLM и анализ траектории действий агента.
- A.1–A.5 — уроки вводной последовательности, не отдельные макромодули.

## 5. Устранение противоречия

Документ `CURRICULUM_SPECIFICATION.md` из `ai-interpretability-course` предлагает альтернативную последовательность модулей 11–26, не совпадающую с решением 2026-11-05. Поэтому он не должен использоваться как основание для переименования или перенумерации Track A. Его содержательные элементы можно использовать как предложения и источники, после проверки на соответствие канонической архитектуре.

В нём также дублируется раздел 1.1 с разными описаниями границ Track B. Для предотвращения дальнейшего расхождения этот документ следует считать историческим источником, а не обновлять каталог по нему автоматически.

## 6. Ограничение текущего каталога

Каталог v3 пока имеет статус `migration_staging` и draft version. В нём существуют 5 Theme UID и 27 Module UID для более детализированной Track A структуры, а также 52 Lesson UID. Это не совпадает один-к-одному с 16 макромодулями 11–26. Поэтому связь макромодулей с Theme/Module UID может быть many-to-many. Track B 27–39 и Track C C0–C12 пока не имеют полного набора catalog UID.

Нельзя:
- создавать фиктивные UID;
- присваивать один lesson UID нескольким несвязанным понятиям;
- удалять старые IDs или менять URL без alias;
- менять published/review статус только ради соответствия карте;
- переводить draft catalog в production без CI, consumer audit и миграции alias.

## 7. Следующие действия

1. Расширить catalog schema поддержкой macro curriculum mapping или отдельной таблицей `curriculum_module_mappings`.
2. Привязать фактические Theme/Module/Lesson UID и legacy IDs.
3. Добавить отдельные UID для Track B и Track C только после утверждения их детализации.
4. Пройти lesson-level QA и проверить все RU/EN/中文 версии, иллюстрации, labs и assessment.
5. Подключить prerequisite diagnostic routes как проверяемые competency gates.
