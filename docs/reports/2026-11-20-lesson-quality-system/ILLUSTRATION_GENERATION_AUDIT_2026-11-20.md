# Аудит генерации иллюстраций урока 7.2.2

**Дата:** 2026-11-20  
**Страница:** `lessons/a-7-2-2-les-a-0172.html`  
**Файлы:** `scripts/xai-permutation-importance-lesson.js`, `lessons/data/xai-05-permutation-importance.js`, `styles/xai-permutation-importance-lesson.css`  
**Результат:** подтверждён дефект диспетчеризации SVG; выявлены архитектурные пробелы измерения текста и browser acceptance. Исправление генератора не выполнялось в рамках этого аудита.

## 1. Подтверждённые причины

### 1.1. Ошибка выбора типа схемы

Renderer проверяет маркеры так:

- `if (s.includes("diagram")) svg(false)`
- `if (s.includes("diagram2")) svg(true)`

Маркер `diagram2` включает подстроку `diagram`. Поэтому секция с `diagram2` получает обе SVG-схемы: первую и вторую. Это детерминированная ошибка, подтверждённая исходным кодом. Маркеры нужно проверять как точные токены/типы, а не через substring.

### 1.2. SVG-текст не имеет механизма переноса

Обе схемы создаются строковой SVG-разметкой с фиксированными координатами, font-size и геометрией. Используются одиночные элементы `<text>`; автоматический перенос слов не реализован. Длина локализованных строк не измеряется, высота панелей не пересчитывается. Поэтому подпись может выйти за рамки узла или пересечь соседнюю стрелку/панель, даже когда её bounding box остаётся внутри общего SVG viewBox.

### 1.3. Схемы не имеют адаптивного layout по содержимому

Размеры панелей, отступы, координаты стрелок и подписей заданы вручную. CSS сжимает SVG на широких экранах и оставляет фиксированную ширину 680px на узких экранах с прокруткой. Прокрутка предотвращает сжатие, но не исправляет переполнение текста внутри узлов и не гарантирует, что все элементы находятся в пределах своих панелей.

### 1.4. Текущий browser gate проверяет недостаточные инварианты

Тест 7.2.2 проверяет число SVG, границы текстовых bounding boxes относительно общего viewBox и общий page overflow. Но:
- не проверяет пересечения подписей с границами их прямоугольников/узлов;
- не проверяет пересечения текстовых bounding boxes между собой и со стрелками;
- не проверяет, что SVG относится к ожидаемому типу и присутствует ровно один раз в соответствующей секции;
- не проверяет реальную читаемость подписи после масштабирования и в каждой локали;
- проверка `svg.scrollWidth <= svg.clientWidth` не доказывает, что содержимое figure viewport доступно пользователю.

Таким образом CI мог пройти при визуально сломанной схеме.

## 2. Рекомендуемая целевая архитектура

### A. Типизированная модель схем

Хранить схемы не в виде маркерных строк внутри массива раздела, а в явном объекте данных, например:

- `type: "pfi-workflow"` или `type: "correlated-feature-importance"`;
- локализованные title, description, node labels, captions;
- декларативные узлы, связи, группы, semantic roles;
- layout constraints: минимальная ширина узла, padding, максимальная длина строки, размеры шрифта.

Renderer выбирает схему по точному `type` из whitelist. Никаких `includes("diagram")` и HTML-фрагментов, собранных из пользовательского/локализованного текста.

### B. Layout до генерации SVG

Для каждого узла измерять текст выбранным шрифтом и текущей локалью; переносить по словам в строки через `<tspan>`; высоту узла рассчитывать из числа строк, line-height и padding. Затем располагать узлы/стрелки с минимальными отступами, пересчитывать viewBox по реальным границам всех элементов.

Если текст не помещается даже при минимальном размере шрифта, не уменьшать его бесконечно: увеличивать схему или переводить узел в вертикальную компоновку. Для очень длинных описаний использовать подпись/легенду вне узла, сохраняя краткий label внутри.

### C. Единый SVG component API

Создать общий компонент диаграмм, который принимает структурированные данные и возвращает SVG с:
- уникальными title/desc IDs;
- viewBox, рассчитанным из полного layout;
- группами узлов/связей;
- доступными текстовыми подписями;
- theme tokens из дизайн-системы;
- контролируемой типографикой и line-height;
- корректными `text-anchor`, `dominant-baseline`, `vector-effect` где применимо.

Не использовать автоматическое сжатие всего SVG для «вписывания» длинных подписей: оно уменьшает шрифт и скрывает проблему.

### D. Стратегия адаптивности

- Desktop/tablet: SVG масштабируется по ширине только если итоговый размер текста остаётся выше установленного минимума.
- Mobile: горизонтальная прокрутка внутри figure допустима для сложной схемы; добавить видимый индикатор прокрутки/подсказку и не обрезать SVG через `overflow:hidden`.
- Простые схемы на mobile перестраивать в вертикальный flow, а не уменьшать до нечитаемого размера.
- Проверять весь диапазон RU/EN/中文: длина строк существенно различается.

## 3. Обязательные quality gates для каждой схемы

1. **Маркер и идентичность:** каждый diagram type распознаётся точно; ровно одна схема в требуемом месте; ожидаемое число узлов и связей.
2. **ViewBox containment:** bounding box каждого видимого SVG элемента целиком внутри viewBox с допуском.
3. **Node containment:** текст каждого узла находится внутри соответствующей панели с заданным padding.
4. **Collision detection:** пересечения текста с соседними узлами, стрелками, линиями и другими текстовыми блоками отсутствуют, кроме явно разрешённых.
5. **Text wrapping:** каждый label имеет ограниченное число строк; нет обрезки через `textLength`/clipPath как маскировки проблемы.
6. **Minimum font size:** после фактического browser render подписи не меньше согласованного минимума (рекомендация: 14 CSS px desktop, 13 CSS px mobile для вторичных подписей; ключевые labels — не меньше 14 px).
7. **Contrast:** контраст каждой подписи измеряется относительно реального фона её узла в light/dark.
8. **Responsive:** 375 / 768 / 1440 px; нет page overflow; figure viewport и доступность прокрутки проверяются отдельно.
9. **Localization:** тестировать все три языка, включая наиболее длинные строки, не только наличие переводов.
10. **Screenshot regression:** сохранять скриншоты схем по каждой локали, теме и контрольной ширине; image diff должен иметь согласованный порог и ручной review для значимых изменений.

## 5. Реализация и результаты проверки

- Создан общий `scripts/lesson-svg-renderer.js`; SVG строится из структурированной спецификации, а не из строковой SVG-разметки в lesson renderer.
- Текст измеряется через Canvas; длинные подписи переносятся, включая китайские строки без пробелов; высота узлов и `viewBox` рассчитываются по фактическому содержимому.
- `diagram` и `diagram2` теперь определяются как точные типы. Вторая секция больше не может случайно запустить первый renderer по совпадению подстроки.
- Общий renderer подключён в RU / EN / 中文 урока 7.2.2 и включён в canonical shell для будущих уроков.
- Browser acceptance проверяет точное число и тип схем, а также попадание каждой подписи внутрь её узла на 375 / 768 / 1440 px, во всех трёх локалях и обеих темах.
- Полный workflow `Deploy static website to GitHub Pages` для `581e977e7cd7e6fdbb07599c10a3072e108b2326` завершился `success`: validate, Supabase migration validation, browser acceptance и deploy прошли.

Ручной pixel-level review production страницы не заявляется: прямое открытие `dchai.ru` через доступный web preview завершилось ошибкой доступа. Нужна визуальная проверка пользователем после обновления страницы. Screenshot baseline / image-diff regression остаётся следующим этапом. Урок 7.2.2 остаётся в `review`.
