# Аудит текущего состояния AI Research DCH School

- **Дата:** 5 ноября 2026 года
- **Ветка:** `main`
- **Репозиторий:** https://github.com/Dach1980/ai-research-dch-school
- **Основание:** независимое чтение файлов текущей ветки GitHub через GitHub API; проверка наличия страниц и файлов по точным путям. Production deployment и визуальное тестирование браузера в рамках этого аудита не подтверждались.

## 1. Краткий итог

Сайт уже является работающим статическим образовательным сайтом с тремя направлениями, двумя полноценными опубликованными уроками Track A, картой знаний, обычным каталогом, новостной страницей и заготовкой авторизации Supabase.

Но это пока **публичная первая версия / MVP витрины**, а не полноценная учебная платформа:
- контент-каталог ещё не подключён к интерфейсу как единый источник истины;
- страницы карты, каталога и Track A содержат дублируемые вручную сведения об уроках;
- Track B и Track C ссылаются на страницы первых уроков, которых нет в `main`;
- регистрация и доступы зависят от внешней настройки Supabase и не должны считаться готовыми;
- административная страница — только read-only прототип, без защищённого входа и операций управления контентом;
- юридические документы регистрации остаются черновиками.

## 2. Готовность учебных материалов

Метаданные, подтверждённые самими страницами:

- A.2: 50–60 минут, начальный уровень, после A.1.

На странице Track A явно указано, что первые пять уроков относятся к модулю 11. На текущей странице опубликованы только A.1 и A.2; A.3–A.5 обозначены как готовящиеся.

Рекомендованная последовательность: сначала A.3, затем A.4, затем A.5. Это продолжает логику первых двух опубликованных планет и закрывает фундаментальный блок до перехода к XAI. Это рекомендация по учебной последовательности, а не утверждение о готовности материалов.

### 2.3 Track B и Track C

Страницы направлений существуют:
- `tracks/inside-ai.html`
- `tracks/building-with-ai.html`

Но в них присутствуют ссылки на отсутствующие страницы:
- `lessons/b1-1-mechanistic-interpretability.html`
- `lessons/c0-1-local-vs-cloud-llm.html`

Обе страницы не найдены в текущей ветке `main`. Поэтому эти ссылки являются дефектом навигации. До подготовки полных уроков их следует заменить на явный статус «готовится» или отключённую карточку, а не показывать как доступные уроки.

Track B и Track C имеют описания и списки модулей, но в проверенных публичных путях нет опубликованных страниц уроков этих направлений.

### 2.4 Материалы подготовки, не равные готовым урокам

В проектном журнале и документации присутствуют аналитические материалы по учебной программе, в том числе:
- архитектура Track A из 16 модулей;
- аудит и педагогическая декомпозиция отдельных модулей AI Interpretability School;
- проектные breakdown-документы для будущих уроков.

Эти документы полезны как база разработки, но сами по себе не являются готовыми публичными уроками. Предложенные декомпозиции и внешние тематические блоки нельзя автоматически считать утверждёнными планетами без проверки crosswalk, зависимостей и редакционной подготовки.

## 4. Что пока не является рабочей функциональностью

### 4.1 Единый каталог

На момент аудита исходные страницы вручную содержат сведения об уроках. Каталог из JSON не был подключён к карте, каталогу и странице Track A.

В ходе текущей работы создана первая каноническая версия каталога в:
- `data/catalog/tracks.json`
- `data/catalog/modules.json`
- `data/catalog/lessons.json`
- `data/catalog/planets.json`
- `data/catalog/schema.json`

В каталог внесены три направления, один подтверждённый модуль 11 и только два реально опубликованных урока A.1/A.2. A.2 имеет prerequisite A.1, поскольку сама страница прямо обозначает «После A.1». Интерфейс пока не переключён на чтение этих JSON-файлов; это отдельная следующая задача.

### 4.2 Валидация каталога

Временные артефакты Этапа 1 Manus не присутствовали в `main` на момент проверки. Вместо переноса непроверенной реализации создан собственный валидатор:
- `scripts/validate-catalog.py`
- `requirements-catalog.txt`
- `.github/workflows/validate-catalog.yml`

Валидатор использует настоящий `Draft202012Validator` из библиотеки `jsonschema` и отдельно проверяет межфайловые инварианты:
- уникальность ID;
- существование Track и Module;
- соответствие направления урока направлению модуля;
- существование всех prerequisite ID;
- запрет self-prerequisite и циклов зависимостей;
- корректный порядок длительности;
- непустой массив `learning_outcomes`, если поле задано;
- соответствие опубликованных уроков планетам;
- запрет планет для неопубликованных уроков;
- только относительные HTML URL без внешних схем, ведущих слешей и traversal-сегментов;
- физическое существование локальных HTML-страниц.

**Статус проверки:** workflow добавлен, но результат его выполнения должен быть подтверждён по GitHub Actions после завершения run. В этом отчёте не заявляется, что CI уже прошёл.

### 4.3 Supabase и защищённый доступ

В `scripts/supabase-config.js` уже записаны Supabase URL и публичный publishable key. Само наличие конфигурации не подтверждает работоспособность проекта, SMTP, email verification, callback или политик доступа.

В `docs/setup/SUPABASE_SETUP.md` указано, что необходимо применить две миграции:
- `supabase/migrations/001_learning_access.sql`
- `supabase/migrations/002_seed_lesson_catalog.sql`

Обе миграции найдены в текущей ветке: `supabase/migrations/001_learning_access.sql` и `supabase/migrations/002_seed_lesson_catalog.sql`. Первая создаёт profiles, lesson_catalog, lesson_content и lesson_entitlements, включает RLS и задаёт политики чтения. Вторая содержит seed-записи каталога. Документация прямо предупреждает: статические файлы GitHub Pages и содержимое публичного репозитория доступны независимо от формы входа; RLS не защищает файлы, закоммиченные в публичный репозиторий.

Следовательно, платный/закрытый доступ нельзя включать до выноса закрытых материалов в Supabase Storage/таблицы с корректным RLS либо в доверенный backend, а затем проверки прямых анонимных запросов.

### 4.4 Юридические документы

- `docs/legal/TERMS_DRAFT.md`
- `docs/legal/PRIVACY_POLICY_DRAFT.md`

Оба файла прямо обозначены как черновики, не утверждённые для публикации. Перед открытой регистрацией необходимы окончательные пользовательские документы и проверка применимого законодательства.

### 4.5 Административная панель

`admin/index.html` прямо предупреждает, что это статический интерфейс GitHub Pages, не защищённый авторизацией. Вкладки переключаются клиентским JavaScript; журнал загружается из `data/audit-roadmap.json`. Изменение контента через UI не реализовано. Атрибут `noindex` не является защитой доступа.

## 5. Приоритетный план доведения до рабочей версии

### Этап 1. Завершить базовую модель контента

1. Получить успешный GitHub Actions run для JSON Schema и cross-reference validator.
2. Добавить тесты на ошибочные fixtures: внешний URL, несуществующий prerequisite, пустые outcomes, цикл, отсутствующая страница, planet → unpublished.
3. Добавить README к каталогу с контрактом данных и правилами публикации.
4. Проверить и исправить отсутствующие ссылки Track B/C.

### Этап 2. Завершить первые пять уроков Track A

1. Подготовить A.3 «Как машина учится на данных».
2. Подготовить A.4 «Что такое модель машинного обучения».
3. Подготовить A.5 «Как проверяют качество модели».
4. Проверить, что A.1–A.5 образуют последовательный фундаментальный блок и не дублируют друг друга.
5. Публиковать каждый урок только после полного редакционного и технического аудита.

### Этап 3. Подключить единый каталог к сайту

1. Сделать общий JS-модуль загрузки каталога с корректной поддержкой GitHub Pages base path.
2. Перевести каталог лекций на JSON.
3. Перевести карту знаний на JSON, сохранив карту и обычный список.
4. Перевести страницу Track A на JSON.
5. Проверить согласованность количества опубликованных уроков и планет во всех представлениях.
6. Добавить автоматическую проверку внутренних ссылок.

### Этап 4. Подготовить безопасную авторизацию

1. Проверить реальные Supabase migrations и применить их в проекте.
2. Проверить email confirmation, SMTP, callback и reset password.
3. Настроить RLS и проверить anonymous/user access.
4. Вынести закрытые материалы из публичного GitHub.
5. Не полагаться на frontend-скрытие ссылок как на контроль доступа.
6. Подготовить окончательные юридические документы до публичной регистрации.

### Этап 5. Превратить прототип в рабочую платформу

1. Определить доверенную серверную границу для публикации и управления контентом.
2. Реализовать защищённую авторизацию администратора и роли.
3. Реализовать workflow черновик → проверка → публикация → снятие с публикации.
4. Реализовать CRUD для Track/Module/Lesson/Planet и аудит изменений.
5. Реализовать пользовательский прогресс, если он входит в минимальную версию продукта.
6. После появления backend подключить панель управления к API; не давать GitHub Pages напрямую изменять репозиторий с клиентской стороны.

## 6. Рекомендуемый следующий учебный материал

**Следующим формировать A.3 «Как машина учится на данных».**

Предлагаемая содержательная граница A.3:
- выборка и наблюдение;
- признаки и целевая переменная;
- обучающие примеры и разметка;
- модель как параметризованная функция;
- функция потерь;
- оптимизация параметров;
- train/validation/test как разные роли данных;
- обобщение, переобучение и недообучение;
- контролируемый небольшой эксперимент и самостоятельная интерпретация результата.

A.4 после этого должна отдельно объяснить, что именно называется моделью, какие у неё параметры, структура, состояние после обучения и чем модель отличается от алгоритма обучения и AI-системы. A.5 должна перейти к метрикам, базовым линиям, разделению данных, leakage, выбору порога и корректной оценке на новых данных.

Этот план — рекомендация по последовательности разработки на основании названий и текущего состава уроков; подробные learning outcomes для A.3–A.5 следует утвердить перед написанием страниц.

## 7. Ограничения аудита

- Проверено содержимое текущей ветки GitHub `main`, а не временной рабочей копии Manus.
- Наличие файлов проверялось по точным путям. Отсутствие файлов B1.1/C0.1 подтверждено ответами GitHub API 404 для указанных путей.
- Веб-инструмент не смог открыть production URL GitHub Pages, поэтому визуальный рендеринг, фактическую доступность всех URL и завершённость последнего Pages deployment этим аудитом не подтверждаем.
- SQL migrations найдены и прочитаны в репозитории, но их применение, фактическое состояние RLS, внешняя конфигурация Supabase, SMTP и end-to-end auth не проверялись в живом Supabase-проекте.
- Не выполнялось полноценное браузерное тестирование desktop/mobile, accessibility-аудит и тестирование форм с реальной почтой.
