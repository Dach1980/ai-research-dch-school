## 6. Сравнение моделей URL

### Вариант A — текущие HTML-адреса

Пример:

`/lessons/a-1-what-is-artificial-intelligence.html`

Преимущества: понятный slug, совместимость с GitHub Pages, отдельными HTML-страницами, SEO и внешними ссылками. Недостаток: при переименовании slug необходимо поддерживать старый адрес или redirect.

### Вариант B — семантическая иерархия

Пример:

`/learn/track-a/module-11/a-1/`

Преимущества: пользователь видит направление, модуль и ID урока; структура подходит для роста каталога и SEO. Нужно обеспечить стабильность адреса при переименовании Track или модуля, а на GitHub Pages — создавать соответствующие каталоги и index-файлы либо генерировать страницы.

### Вариант C — числовая адресация

Пример:

`/learn/7/0/0`

Преимущества: короткий адрес и удобство для клиентского приложения с индексной навигацией. Недостатки: адрес не объясняет содержание, хуже подходит для SEO и может стать нестабильным при перестановке элементов. На GitHub Pages без fallback-механизма такая маршрутизация сложнее.

### Рекомендация исходного аудита

Сейчас не менять URL опубликованных уроков. Сохранить существующие HTML-адреса как обратноссовместимые. В дальнейшем можно рассмотреть семантический вариант B через адаптер и redirect-совместимость. Числовой вариант C не использовать как единственный постоянный публичный адрес урока.

## 7. Дополнительные замечания при разборе отчёта

Следующие пункты — не выводы Manus, а замечания к фрагментам кода и схемы, приведённым в приложенном отчёте. Их необходимо проверить на самих файлах перед переносом в production.

1. **Регулярное выражение URL выглядит ошибочным.** В `schema.json` и `validate-catalog.py` указано выражение с фрагментом `(?!https?:// )` — после `//` стоит пробел. Поэтому проверка может не блокировать внешний URL вида `https://example.com/page.html`, как, вероятно, предполагалось. Следует заменить проверку на явное разрешение только относительных путей и отдельно запретить схемы, ведущие слеш и traversal-сегменты.
2. **Проверка предварительных требований неполная.** Валидатор проверяет формат ID в `prerequisites`, но в показанном коде не проверяет, что каждый такой ID существует в каталоге, не ссылается на сам урок и не образует цикл зависимостей.
3. **Проверка learning outcomes допускает пустой список.** Условие `any(...)` не выдаст ошибку для пустого массива, хотя сообщение об ошибке говорит о непустом массиве.
4. **Не все поля проверяются одинаково строго.** В показанном валидаторе `track.status` и `module.status` проверяются только как непустые строки; формат `planet_id` отдельно не проверяется; некоторые ограничения из JSON Schema не повторены в Python-коде.
5. **Обработка неверного корневого типа JSON может завершиться исключением.** Функция `load()` добавляет ошибку, если корень не объект, но возвращает исходное значение; дальнейшие функции ожидают словарь и могут вызвать дополнительную ошибку выполнения.
6. **Нужна реальная проверка JSON Schema.** Следует запускать стандартный валидатор JSON Schema Draft 2020-12 в CI или отдельной проверочной среде, а автономный Python-валидатор оставить для межфайловых инвариантов и проверки локальных HTML-путей.
7. **Нужно проверить семантику `catalog-paths.js`.** По показанному коду неизвестный путь возвращает `/`. Для GitHub Pages проект должен гарантированно использовать `/ai-research-dch-school/`; поведение для production, локального preview, custom domain и неизвестного pathname следует покрыть тестами.

Эти замечания не отменяют полезность выбранной архитектуры, но означают, что до переноса каталога в production нужно исправить и повторно проверить валидатор и helper.

## 8. Решения и границы следующего этапа

На основании исходного аудита можно зафиксировать:

1. Единый JSON-каталог — правильная основа для синхронизации карты, каталога уроков и страниц направлений.
2. В каталоге пока должны находиться только реально подготовленные и опубликованные уроки.
3. Планеты должны ссылаться на уроки по ID и не дублировать учебные данные.
4. Существующие публичные URL A.1 и A.2 пока сохраняются.
5. GitHub Pages остаётся production-хостингом; Manus используется для разработки и временного preview.
6. Этап 2 не считается согласованным или выполненным только на основании этого отчёта. Его нужно запускать отдельно после переноса и проверки артефактов Этапа 1.

### Предлагаемый порядок дальнейших действий

1. Получить от Manus сами файлы Этапа 1 по указанным путям и сверить их с содержимым, приведённым в исходном отчёте.
2. Перенести согласованные файлы в GitHub и запустить проверки непосредственно в репозитории.
3. Исправить выявленные пробелы в schema, валидаторе и base-path helper.
4. После успешной проверки отдельно согласовать Этап 2 — подключение каталога к интерфейсу, начиная с каталога уроков и затем карты знаний.
