# DCH School — Roadmap модернизации учебной платформы

**Дата фиксации:** 2026-11-08  
**Статус:** approved roadmap; выполнение этапов 1–4 начато  
**Рабочая ветка:** main

## Цель

Закрепить единую архитектуру учебного каталога, дизайн-систему, стандарт визуализации кода, методику объяснения программного кода и требования к иллюстрациям. Сначала создаётся общая основа сайта; затем на ней проводится контрольная переработка A.1.2.1. Новые уроки до завершения контрольной приёмки не создаются.

## Принятая иерархия

- **Track** — устойчивый буквенный код и название направления: Track A — Understanding AI.
- **Theme** — код вида A.1 и общее название темы: Theme A.1 — «Основы AI и машинного обучения».
- **Module** — содержательное название без дополнительного цифрового кода: например, «Что такое AI».
- **Lesson** — код темы и порядковый номер урока: A.1.1, A.1.2 … A.1.6.
- Нумерация уроков продолжается между модулями одной темы.
- При переходе к новой теме нумерация начинается заново: первый урок Theme A.2 — A.2.1.
- Технические идентификаторы сущностей не зависят от отображаемых кодов.

## Этапы

### 1. Аудит и архитектура каталога
Инвентаризировать Track / Theme / Module / Lesson, URL, языки, статусы, prerequisites и planet references. Определить все места, где отображаются коды и названия. Подготовить mapping старых кодов в новые. Проверить зависимости каталогов v1/v2, адаптеров, валидаторов, Supabase и страниц. Не выполнять разрушительную миграцию до появления стабильных технических ID и compatibility tests.

**Результат:** COURSE_HIERARCHY.md и документированная карта миграции.

### 2. Миграция каталога и навигации
Ввести отдельные стабильные технические ID и пользовательские display codes. Перевести модульные названия из псевдокодов в названия. Перенумеровать уроки в пределах темы, включая продолжение нумерации между модулями. Сохранить URL либо настроить проверяемые redirects/alias mapping. Обновить каталоги, карточки, хлебные крошки, planet map, языковые версии, prerequisites и backend references. Добавить тесты отсутствия дубликатов и dangling references.

**Условие переключения:** только после полного аудита всех потребителей каталога и успешного CI. До этого старый production catalog остаётся совместимым.

### 3. Дизайн-система
Вернуть theme switcher в общий header и reader header. Поддержать Light / Dark / System, сохранение выбора и системную тему по умолчанию. Использовать единые design tokens для фона, текста, поверхностей, границ, ссылок, состояний и фокуса. Обеспечить контраст иллюстраций, схем, подписей, таблиц и карточек в обеих темах. Проверить keyboard focus, reduced motion и мобильную компоновку.

### 4. Кодовые блоки и учебная подача
Ввести единый компонент code block с подсветкой синтаксиса, нумерацией строк, копированием и адаптивной прокруткой. Различать ключевые слова, функции/методы, классы/типы, строки, числа, переменные, комментарии и операторы. Для каждого существенного фрагмента указывать язык и назначение. Разделять длинные программы на небольшие логические блоки. Перед блоком объяснять цель; после — разбирать новые операторы, функции и параметры, логику, результат, практический эксперимент и типичные ошибки.

### 5. Контрольный урок A.1.2.1
Переработать код и иллюстрации по новым стандартам. Сверить RU / EN / 中文. Проверить обе темы, desktop/mobile, клавиатуру и screen reader. Сохранить статус review до закрытия quality gate.

### 6. Приёмка
Автоматические тесты каталогов, ссылок, стилей, языковых версий и кодовых блоков. Ручная визуальная приёмка в браузерах desktop/mobile. Accessibility-проверка и контроль контраста. Публикация только после прохождения quality gate.

### 7. Масштабирование
После приёмки контрольного урока применить стандарты к существующим материалам и затем продолжать курс последовательно.

## Ограничения миграции

- Не использовать display code как первичный технический ключ.
- Не менять опубликованные URL без redirect/alias и теста.
- Не менять lesson status автоматически.
- Не создавать новые уроки в рамках этапов 1–4.
- Не считать CI заменой ручной визуальной приёмки.
- Все изменения вести на main в небольших проверяемых коммитах.
