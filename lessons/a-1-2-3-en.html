1.2.3 — Data Types and Feature Representation

Numerical, categorical, temporal and text features: identify their meaning, choose representations and avoid common data preparation errors.

Learning outcomes

After this lesson, you will be able to:

  • Distinguish numerical, nominal, ordinal, temporal and text features.
  • Explain why feature type depends on meaning, not only storage format.
  • Choose basic categorical encodings and understand their limitations.
  • Detect unit, scale and date representation errors.
  • Draft a feature preparation plan before model training.
Key questionA column may look numeric but actually contain category codes. A date may be stored as text, a number or a calendar event. How do we choose a representation that preserves the meaning needed by a model?

1. Meaning comes before data type

A file's storage type and an analytical feature type are not the same. The value `17` might be an age, room number, region code or event count. Arithmetic is meaningful for some of these, but not all.

Describe what each field means, its valid values, units and when it becomes available. A CSV format or pandas column dtype is a technical clue, not a semantic definition.

2. Numerical features

Quantitative features express measured quantities or counts. Continuous values can vary within a range (temperature, area); discrete values commonly count items (requests, floors).

Check units and ranges. Celsius and Fahrenheit are different scales; square metres and square feet must not be mixed without conversion. Zero may mean absence or may be an arbitrary point on a scale. Not every numeric field should be averaged.

3. Nominal and ordinal categories

A nominal category identifies a class without a natural order: building type, region or request type. An ordinal category has a meaningful order, but distances between levels need not be equal: low, medium, high.

Codes 1, 2 and 3 for regions do not make regions quantitative. A model may interpret their numeric order and differences as information. One-hot encoding is common for nominal categories; ordinal encoding is justified only when the order is real and its limitations are understood.

4. Encoding categories

One-hot encoding creates an indicator for each category. It does not impose an artificial order, but increases the number of columns. High-cardinality fields can create very wide feature spaces.

Ordinal encoding replaces categories with codes and is appropriate when order is meaningful or the model and encoding scheme explicitly handle categorical data. Frequency and target encoding need care: compute statistics only within training folds to avoid leakage. Define how unseen categories will be handled.

5. Dates and time

A date is more than a string. It can yield year, month, weekday, hour, season or elapsed time since an event. The right features depend on the question and prediction time.

Account for time zones, daylight-saving transitions, missing values and calendar cycles. For periodic values such as hour of day or weekday, sine/cosine features can express that 23:00 and 00:00 are close even though their numeric values differ.

6. Text and identifiers

Text fields may be free-form text, short labels or structured codes. Free text can be represented with tokenization, bag-of-words, TF-IDF or embeddings depending on the task and resources.

An identifier is useful for joining records, grouping and auditing, but is not necessarily a feature. A unique ID may let a model memorize rows or indirectly reveal the target. Including it requires a scenario-specific justification and leakage checks.

7. Scaling and transformations

Scaling changes a numeric range; standardization, for example, centers a feature and divides by its standard deviation. It matters for scale-sensitive methods but is not required for every algorithm.

Transformations such as logarithms may help a model, but must respect meaning and valid values. Any transformation whose parameters are learned from data (means, standard deviations, category vocabularies) must be fitted on train only, usually inside a Pipeline.

8. Practice: build a feature specification

Consider a table for daily building energy prediction: `building_id`, `date`, `temperature_c`, `floor_area_m2`, `building_type`, `occupancy_plan`, `occupancy_actual`, `energy_kwh`.

For each field, record meaning, feature type, units or valid categories, availability at prediction time, representation and leakage risk. For tomorrow's forecast, tomorrow's `occupancy_actual` is unavailable; `building_id` may be needed for grouping, but including it in X needs separate justification.

Practical assignment

Create a feature specification for the table. Choose a representation for `building_type`, derive at least two calendar features from `date`, decide whether `temperature_c` and `floor_area_m2` need scaling, and flag fields that cannot be used before the day begins.
